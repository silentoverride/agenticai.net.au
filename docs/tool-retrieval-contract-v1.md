# Tool Retrieval Contract v1

> Built using the Retrieval Record Contract workflow (`rrc-001-v1`).
> Target: `src/lib/server/assessment/tool-lookup.ts` and downstream consumers.
> Status: **SPEC** — ready for implementation.

---

## 1. Problem Statement

The current `lookupToolsForTranscript()` pipeline has four structural issues:

1. **Vague contract** — `AITool` has no reliability signal. A hallucinated tool and a real tool are indistinguishable to the report generator and gate evaluator.
2. **Separate LLM call for extraction** — `extractPainPointsForToolLookup()` adds 10-20s latency and Perplexity cost just to determine what to search for. This information already exists in the transcript.
3. **Fragile enrichment** — `enrichAnalysisWithTools()` uses substring matching to backfill tool URLs, which breaks on minor name variation.
4. **No budget/pricing alignment** — The tool's pricing tier is never compared against customer budget signals, so the report may recommend enterprise tools to a micro-business.

The retrieval contract makes the tool lookup a **testable, auditable, schema-enforced interface** rather than an ad-hoc LLM call.

## 2. Input Contract

### 2.1 Required

| Field | Type | Source | Description |
|-------|------|--------|-------------|
| `transcript` | `string` | AssessmentReportJob | Full intake transcript |
| `callerRole` | `string \| null` | Retell post_call_analysis | Owner, manager, etc. |
| `industry` | `string \| null` | Retell post_call_analysis | SMB industry vertical |
| `teamSize` | `string \| null` | Retell post_call_analysis | Org size signal |
| `currentTools` | `string \| null` | Retell post_call_analysis | Tools already in use |

### 2.2 Optional (enhance quality)

| Field | Type | Source | Description |
|-------|------|--------|-------------|
| `topPainPoints` | `string \| null` | Retell post_call_analysis | Pre-extracted pain points (if Retell provides them) |
| `budgetSignal` | `{ min: number, max: number, confidence: number } \| null` | Budget detection (PRE-3 eval) | Extracted budget range for pricing alignment |

### 2.3 What Changed

- **Before**: Only `transcript` is passed. Everything else is re-derived by a separate Perplexity call.
- **After**: Transcript + structured Retell metadata injected. Eliminates the separate `extractPainPointsForToolLookup()` LLM call entirely. Pain points are either already in Retell data or derived from the transcript in the main analysis prompt (which already does this).

## 3. Output Contract — `RetrievalRecord[]`

Each returned tool is a `RetrievalRecord` with these fields:

```typescript
interface RetrievalRecord {
  // === Identity ===
  name: string;                          // exact product name (e.g., "Jasper AI")
  url: string;                           // verified product URL (vendor site, not aggregator)

  // === Classification ===
  category: string;                      // pain point this addresses (match to pain_point.title)
  categories_secondary: string[];        // other pain points it could address
  
  // === Pricing ===
  pricing_tier: 'free' | 'freemium' | 'starter' | 'professional' | 'enterprise' | 'unknown';
  pricing_monthly_usd_min: number | null; // minimum monthly cost (null if unknown)
  pricing_monthly_usd_max: number | null; // maximum monthly cost (null if unknown)
  pricing_note: string;                  // human-readable pricing description
  
  // === AU Availability ===
  available_in_australia: boolean;       // explicitly checked
  au_pricing_available: boolean;         // AUD pricing available (vs USD only)
  au_region_note: string;                // any region-specific notes
  
  // === Reliability ===
  source: 'perplexity_futurepedia' | 'perplexity_taaft' | 'hardcoded_catalogue' | 'llm_generated';
  confidence: number;                    // 0.0-1.0: how confident the tool data is accurate
  verified_at: string;                   // ISO 8601 timestamp of search
  
  // === Business fit ===
  budget_alignment: 'within_budget' | 'above_budget' | 'below_budget' | 'no_budget_signal';
  team_size_fit: 'solo' | 'small_team' | 'mid_market' | 'enterprise' | 'unknown';
  
  // === Metadata ===
  one_line_description: string;          // what it does
  search_query_used: string;             // which search query produced this result
  cache_hit: boolean;                    // was this from cache?
}
```

## 4. Contract Guarantees

The retrieval layer guarantees:

1. **No hallucination pass-through** — `confidence < 0.4` tools are NOT returned. If a tool was generated by the LLM without source verification, it carries `source: 'llm_generated'` and `confidence < 0.4`, and is stripped.

2. **AU availability is non-negotiable** — Every tool must have `available_in_australia` explicitly checked. If the search cannot determine availability, it's `false` with a note.

3. **Pricing is structured, not prose** — `pricing_monthly_usd_min/max` are numeric, not strings like "starts at $19/month." This enables programmatic budget alignment checking.

4. **Source provenance is tracked** — Every tool carries its `source` and `verified_at` timestamp. The report generator and gates can use this to weight recommendations by reliability.

5. **Cache freshness is explicit** — `cache_hit` and `verified_at` together give consumers full visibility into data freshness. The gate PRE-2 eval uses these fields.

---

## 5. Budget Alignment Contract

The retrieval layer computes budget alignment when `budgetSignal` is provided:

```
within_budget:    pricing_monthly_usd_max <= budgetSignal.max * 1.2
above_budget:     pricing_monthly_usd_min > budgetSignal.max
below_budget:     pricing_monthly_usd_max < budgetSignal.min * 0.5
no_budget_signal: budgetSignal is null
```

**Gate integration**: `major-project-verification` gate's E1 (budget alignment) uses this field. A tool with `budget_alignment: 'above_budget'` in a recommendation must be justified or it triggers a BLOCK.

## 6. Cache Contract

- **TTL**: 7 days (was 24h — increased because the eval suite now checks freshness explicitly)
- **Cache key**: SHA-256 of `canonicalized(industry + top pain point keywords)`, not raw transcript
- **Invalidation**: On pipeline start, if `cache_hit === true && verified_at < (now - 7 days)`, force a fresh lookup
- **Behavior on cache miss**: Full Perplexity search (one LLM call, not two)

### Why eliminate the extraction call?

The current flow is:
```
transcript → Perplexity (pain point extraction) → pain points → Perplexity (tool search) → tools
```

That's two Perplexity calls. The main LLM analysis (`analyzeTranscript`) already extracts pain points as part of report generation. We don't need to run a separate call just for search keywords. The new flow:

```
transcript + Retell metadata → build search query from existing signals → Perplexity (tool search) → RetrievalRecord[]
```

This eliminates one Perplexity API call per assessment (~$0.01-0.03 savings per report, ~20s latency reduction).

---

## 7. Fallback Contract

| Scenario | Behavior |
|----------|----------|
| Perplexity API key missing | Return `[]` (no tools) — report generated without tool recommendations |
| Perplexity timeout (25s) | Return `[]` — log warning, report proceeds without tools |
| Perplexity returns empty | Return `[]` |
| Perplexity returns unparseable JSON | Return `[]` — log error with raw content snippet |
| D1 unavailable (cache only) | Skip cache, proceed with live lookup |
| D1 + Perplexity both unavailable | Return `[]` — pipeline must not fail due to missing tools |

**No scenario causes pipeline failure**. Tools are enrichment, not a requirement. This is a design rule, not an accident.

## 8. Implementation Changes Required

### 8.1 New Types

Add to `src/lib/server/assessment/types.ts`:

```typescript
export interface BudgetSignal {
  min: number;
  max: number;
  confidence: number;    // 0.0-1.0
  source: string;        // e.g., "transcript_explicit", "industry_average", "inferred"
}
```

Replace `AITool` in `tool-lookup.ts` with `RetrievalRecord` (or keep `AITool` as a legacy alias).

### 8.2 Refactor `tool-lookup.ts`

- Remove `extractPainPointsForToolLookup()` entirely
- Replace `lookupToolsWithPerplexity()` with a version that takes structured pain points (from Retell metadata or the main analysis)
- Add `buildSearchQueryFromMetadata(meta: AssessmentReportJob): string` — deterministic query builder from structured fields
- `lookupToolsForTranscript()` now takes `AssessmentReportJob` (not just `transcript`) and optional `BudgetSignal`
- Return type: `RetrievalRecord[]`

### 8.3 Refactor `pipeline.ts`

- `stageToolResearch()` now receives `job` (not just `transcript`)
- Pass `budgetSignal` from PRE-3 eval into the tool lookup
- Tool results feed into both `stageLlmAnalysis()` AND gate checkpoints

### 8.4 Update `tool-cache.ts`

- TTL → 7 days
- Store `RetrievalRecord[]` (not `AITool[]`)
- Add `invalidateCache()` export for PRE-2 eval usage

### 8.5 Update Gate Definitions

- `major-project-verification` E1 references `budget_alignment` field
- `quick-wins-verification` E2 cross-references tool `source` and `confidence`

## 9. Testability

The contract enables deterministic testing:

```
INPUT:  transcript="We spend 10h/week on invoicing in Xero, $500/month on software, small team of 3"
        budgetSignal={ min: 300, max: 700, confidence: 0.8, source: "transcript_explicit" }

EXPECT: RetrievalRecord[] where:
        - All records have confidence >= 0.4
        - All records have available_in_australia checked
        - budget_alignment is computed per record
        - pricing_monthly_usd_min/max are numeric or null (not strings)
        - search_query_used is populated
        - verified_at is ISO 8601 within last 7 days
```
